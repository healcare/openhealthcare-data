# Research and site-building workflow

Effective September 30, 2026. User-directed division of work for OpenHealthcare.

## Ownership

| Work | Owner | Deliverable |
| --- | --- | --- |
| Source discovery, identity matching, credential lookups, contact conflicts, media provenance | ChatGPT research workflow | Dated claim-level evidence and unresolved findings in healcare/openhealthcare-data |
| Narratives, factual corrections, editorial assessment and release scope | ChatGPT research workflow; user or designated reviewer for decisions requiring actual human review | Versioned content, explicit apply/hold scope, and review decisions |
| Site design, accessible UI, data ingestion, performance, canonical URLs, rendering and technical tests | Replit | Reviewable application changes in healcare/openhealthcare |
| Deployment or indexing changes | Separate explicit user/editorial instruction | Authorized publication decision |

Replit consumes evidence and review decisions; it does not repeat web research, license searches, narrative fact checking, or lengthy editorial/human-review simulations. An AI review is not a human review. Never change pending-human-review to reviewed merely because either agent has read a record.

## Handoff from research to implementation

Each batch names its exact data commit and provides:
- Existing permanent IDs and canonical URLs, or an explicit new-record scope.
- Content and claim-level sources, research dates, actual verification outcomes, and media provenance.
- A concise list of changes to apply, changes to hold, and unresolved facts.
- Expected rendering and focused acceptance checks.

Source-stated content can be implemented with its attribution and pending status intact when the batch permits it. Implementation readiness does not mean independently verified, clinician-approved, ready for indexing, or authorized for deployment. Do not use a directory-wide verified badge.

Replit should continue eligible content and shared UI work while a specific record or field is held. Preserve held content and its current visibility; report the hold once and return the factual question here. Do not re-run an entire batch review or wait on an unrelated fact to finish site building.

## Technical checks in Replit

Check schema compatibility, identity/URL preservation, citation retention, faithful display of supplied statuses, media load failures and fallbacks, keyboard/mobile usability, and relevant regression coverage. Run required project gates once; repeat only failed checks affected by a fix. Report technical failures separately from research questions.

If source links break, evidence conflicts, or an unexpected content problem appears during implementation, record the affected ID, field, source, and observed issue. Return that exception to the research workflow without inventing a correction or undertaking a new research cycle.

A completion report should state the data commit consumed, application commit, applied/held counts, technical test results, and outstanding exceptions. Do not claim deployment when only a preview or commit exists.

## Cost and privacy

Research each claim once per needed refresh and reuse dated evidence within its scope. Send small versioned changes and consolidate exceptions. Prioritize changing or consequential facts over repeatedly rewriting stable biographies. No recurring jobs are created by this document.

Maintain the owner's current Good cookies policy: no third-party tracking or behavioral profiling, no sharing visitor data with publishers, advertisers or data brokers, and minimum necessary processing. Do not restore an absolute zero-cookie or blanket no-advertising promise. Do not add advertising pixels or analytics identifiers. Third-party media references require a separate delivery/privacy assessment before treating them as compatible with that requirement; a source URL alone does not establish privacy or reproduction rights. Replit owns delivery implementation, while research owns provenance.
